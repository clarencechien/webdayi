WebDayi Smart · 技術說明

智慧 2 碼是怎麼猜到字的

大易輸入法一個字要打 4 碼。我們只讓你打 2 碼,剩下的交給機率模型補。 這篇說明它用了哪些統計量(是的,就是你想的 unigram 和 bigram)、 為什麼同樣的資料拿來「預測下一個字」會慘敗、拿來「解碼已經按下的碼」卻夠用, 以及中間那個叫 Viterbi 的動態規劃到底在算什麼。

01 / 問題2 碼會撞成一團

大易是「字形拆碼」的輸入法:一個字最多 4 碼,例如「吃」是 o2c、「個」是 a7o。 打滿全碼幾乎不會有歧義——我們的碼表裡 16,918 個全碼碼位,平均只對應 1.1 個字, 打完就是它了。

但打 4 碼很累。大易的慣例簡碼是取 首碼 + 末碼(吃 o2c → oc, 個 a7o → ao)。這樣按鍵數直接砍半,代價是碼位空間從 16,918 縮到 1,562, 13,052 個字擠進去,平均一個碼位 8.7 個字(中位數 7,最擠的有 62 個)。

用資訊理論的講法:要從 8.7 個候選收斂到 1 個,需要 log₂(8.7) ≈ 3.1 bits 的額外資訊。這 3.1 bits 就是整個系統要去別的地方湊出來的東西。

為什麼是「首碼+末碼」而不是「前兩碼」 首尾碼把字分散得更均勻。改用前兩碼時,同一個部首開頭的字會全部塞在同幾個碼位; 改回首尾碼之後,我們的離線評測準確率從 95.7% 升到 97.4%,詞庫體積也從 3.8MB 掉到 2.4MB。

02 / 關鍵區分「預測未知」和「解碼已知」是兩回事

這個專案先做過一版「Smart Compose」:根據你剛打完的字,猜你還沒打的下一個字,猜中就按 Tab 接受。 它失敗得很徹底,而且是結構性的失敗,不是程式寫壞。

原因可以直接算:中文字元的 bigram 條件熵大約 4–5 bits, 意思是「知道前一個字之後,下一個字仍然有 2⁴~2⁵ ≈ 16–32 個合理選擇」。 要從十幾二十個裡面猜中第一名,命中率天生就只有一兩成——再加上「看建議 → 判斷 → 決定按不按」 的認知中斷成本,體驗必然是負的。

但同樣這 4–5 bits,拿來做解碼就完全夠用:使用者已經按下 2 碼, 候選被壓到平均 8.7 個,只需要 3.1 bits 就能收斂。4–5 > 3.1,綽綽有餘。 同一份 bigram 資料,用在預測是遠遠不夠,用在消歧義是綽綽有餘——差別只在於 使用者有沒有先給你那 2 碼的約束。

03 / 資料三張表,兩種統計量

整個引擎只吃三個 JSON,全部是離線算好的靜態檔,瀏覽器抓下來就能用,沒有伺服器:

檔案裝什麼統計量大小
dayi_db.json碼表:每個大易碼 → 哪些字沒有機率,純查表1.5 MB
word_db.json153,513 個詞(1–4 字)與它們的出現次數詞的 unigram2.4 MB
char_bigram.json83,401 組相鄰字對的次數字的 bigram1.2 MB

所以回答那個問題:是的,就是 unigram 和 bigram,沒有神經網路、沒有 LLM 在跑。 但有一個關鍵設計:unigram 是算在「詞」上,不是算在「字」上。 「吃飯」在詞庫裡是一個條目、出現 585 次;引擎不是把「吃」的字頻乘上「飯」的字頻。 這個差別後面第 06 節會看到它有多要命。

資料哪裡來

詞頻主要取自 McBopomofo(小麥注音) 的 phrase.occ(MIT 授權), 這是台灣正體語境的詞頻表;不足的部分用 rime-essay 的詞頻表補洞,但打了 ×0.005 的重折扣 ——因為它是大陸語料,直接用會讓「哪裏」壓過「哪裡」、「咋」壓過「吃」。 字 bigram 則是從同一批詞條的「詞內相鄰字對」加權統計出來的。

這份 bigram 有個先天缺口 它是從詞表算的,不是從連續文章算的,所以只涵蓋「詞內部」的字對。 像「你吃」這種跨詞的搭配,在表裡根本不存在。 第 05 節的 backoff 就是為了讓這種缺口不要害死解碼。

04 / 演算法把句子攤成一張圖,然後找最短路

使用者連續打 at oc ax bj ob 這 10 個鍵。引擎每 2 鍵切一個 token, 每個 token 去碼表查出它的候選字——這就攤成了一張叫 lattice(格狀圖) 的東西: 每一欄是一個字的位置,欄裡的每個節點是一個可能的字。

解碼 = 在這張圖上挑一條「最有可能」的路徑。候選數平均 8.7,五個字就有 8.7⁵ ≈ 5 萬條路徑, 十個字就是 25 億條,顯然不能一條一條試。 Viterbi 演算法就是解這件事的動態規劃:它從左到右走一次, 在每個節點只保留「走到這裡為止的最佳分數」,後面的計算就只看這個值,不必回頭重算前面。 複雜度從指數變成線性。

分數怎麼算

路徑分數是把整條路徑上每一段的 log 機率加起來(用 log 是為了把連乘變成連加,避免浮點下溢)。 一條路徑被切成若干個詞,每個詞貢獻:

score(路徑) = Σ每個詞 w [ // 詞本身有多常見 log P(w) + (len(w) − 1) × 3.0 // 詞長獎勵 + 2.0 × log(1 + 你選過幾次) // 個人習慣 + 0.3 × log P(w首字 | 前詞末字) // 跨詞黏著 γ ]

四項各自的角色:第一項是詞的 unigram(這個詞在語料裡有多常見); 第二項補償「長詞的機率天生比短詞小」這個偏差,不然引擎會偏好把句子切成一堆單字; 第三項是個人化,等一下第 05 節講; 第四項是字的 bigram,只用在詞與詞的接縫上,而且權重只有 0.3。

γ 這麼小是實測掃出來的:我們掃過 0.15 到 1.0,γ 越大準確率反而越低。 這正好反映了第 03 節那個缺口——這份 bigram 只堪任接縫的黏著劑,不堪任主要訊號。

05 / 三個細節沒有它們就會壞掉的地方

Backoff:沒見過的字對不能判死刑

「你吃」這組字對在我們的 bigram 表裡查不到(它是跨詞搭配,詞表裡沒有)。 最直覺的作法是給它機率 0——但 log(0) 是負無限大,這條路徑就直接出局了, 哪怕「你」和「吃」都是超常用字。

正確作法叫 backoff(退避):查不到 bigram 時,退一步用該字自己的 unigram, 再乘一個折扣係數 β = 0.02 表示「這是猜的,信心打折」:

P(c₂ | c₁) = count(c₁c₂) / count(c₁) // 查得到:正常算 P(c₂ | c₁) = β × P(c₂) // 查不到:退避到打折的 unigram
這個地方以前踩過坑 專案的前一版引擎給未見字對一個固定的 1e-10。結果是: 只要某個冷僻字剛好有一筆垃圾 bigram 紀錄,它就會絕對輾壓所有沒紀錄的常用字。 實測輸出是「你咋餓了嗎」——每個錯字都是冷僻字。 這不是資料稀疏的隨機噪音,是計分公式的結構性缺陷。

詞級解碼:為什麼不是逐字算

前一版還有一個更根本的問題:它在第 2 個字以後完全沒有字頻項,只看 bigram。 於是當一整欄候選的 bigram 全都查不到時,它們分數完全相同,選字實際上是由物件的遍歷順序決定的 ——常用字和冷僻字一視同仁。

現在的作法讓每個位置的頻率資訊永遠存在,因為它內含在詞的機率裡。 而且詞級解碼還順手繞開了那個資料缺口:「吃飯」是詞庫裡的一個條目, 引擎根本不需要問「吃」後面接「飯」的 bigram 是多少。跨詞 bigram 只在接縫處用一次。

個人習慣:你改過的字會被記住

每次你手動改字(或送出一段文字),那個字會被記進瀏覽器的 localStorage, 分數加上 2.0 × log(1 + 次數)。用 log 是為了讓它成長會鈍化—— 選過 1 次加 1.4 分,選過 100 次也只加 9.2 分,不會無限膨脹到壓死全域統計。

效果是:同一個碼你手動改過兩三次之後,那個字就會自己跳出來。 因為 unigram 是算在詞上,這個個人化不會污染既有詞彙的判斷 ——把「查」選熟了,「本來」「根本」「日本人」仍然正確。

06 / 驗收它到底準不準

評測用 159 句台灣正體句子(對話與新聞各半、共 1,240 字), 把每個字轉成 2 碼餵進解碼器,量 top-1 準確率。這份 harness 在 repo 裡,瀏覽器打開就能重跑。

指標結果門檻
2 碼 top-1(有上文)97.4%85%過
2 碼 top-3(有上文)98.2%95%過
句首第一個字(無上文)98.1%—
整句一字不錯84.3%—
整句解碼時間2.3 ms—

top-3 這個數字比 top-1 更重要:2 碼模式下錯字是必然的,決定體驗的是改錯成本。 98.2% 的 top-3 表示——就算第一個猜錯,正確答案幾乎一定就在候選列的前三個,按一下就換掉。 所以介面設計上,候選列永遠對準你剛打的那個字,直接按選字鍵就能替換,不用先點。

剩下的錯誤集中在三類,誠實列出來:

  • 同碼的高頻近義競爭(證/這、設/說、塞/賽):字 bigram 的資訊量不足以區分,屬於 2 碼模式的固有誤差。
  • 詞邊界切錯(存檔 → 在機):需要更強的跨詞模型。
  • 句首的專有名詞:沒有任何上文可用,只能靠字頻。

07 / 小抄名詞對照

Unigram
單獨一個單位出現的機率。我們算在「詞」上:P(吃飯) = 585 / 22,705,017。
Bigram
給定前一個單位,下一個是什麼的條件機率。我們算在「字」上,只用在詞與詞的接縫。
N-gram
unigram、bigram 的統稱(n=1、2)。這個系統沒有用到 n≥3。
Lattice
格狀圖。每一欄是句子的一個位置,欄裡的節點是那個位置的候選字。
Viterbi
在 lattice 上找最高分路徑的動態規劃演算法。從左到右走一次,每個節點只留最佳分數。
Backoff
查不到高階統計時退回低階統計並打折,避免把「沒見過」誤判成「不可能」。
條件熵
知道前文之後,下一個字還剩多少不確定性,單位是 bit。中文字元 bigram 約 4–5 bits。

原始碼與資料:smart/js/decoder.js(引擎,約 200 行)、 converter/build_smart_db.py(離線資料管線)、 smart/tests/eval.js(評測 harness)。
